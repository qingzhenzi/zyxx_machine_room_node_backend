# QEStudio 产品路线与范围决策

> 2026-11-14 决策记录。当前阶段以比赛演示为主，但下述方向保留为后续产品路线。
> **代码不删除，只隐藏 UI 入口**；后端、路由、数据表、文档继续保留。

## 1. 多房间：保留，即使只有一个设备

多房间不是可选功能，而是系统的管理底座：

- 房间是设备槽位、镜像默认底包、启动配置、工单范围、隔离网络、监控聚合的挂载点；
- 即使比赛现场只有一个房间、几台设备，也应按“区域 → 房间 → 设备/机器”组织，否则设备、镜像、启动配置都会退化成全局单例，后续无法扩展；
- 演示可用 1 个区域 / 2 个房间 / 2–3 台设备，真实教室可按房间复制。

### 后续方向：联邦与多房间统一管理

- 多控制节点（校区/教室节点）注册与心跳；
- 统一视图：跨节点房间、设备、镜像版本、健康状态；
- 远程运维：镜像分发、启动配置下发、WOL/关机、诊断与告警；
- 安全边界：节点间 mTLS、租户/房间隔离、操作审计；
- 联邦不是“多房间”的前提：先把单节点多房间做稳，再叠加跨节点同步。

## 2. 排课与事件：当前隐藏，未来按“计划 + 例外”设计

### 现状（2026-11-14）

- 课表看板、排课计划、触发事件（课表事件）相关**导航入口和主要页面展示已隐藏**；
- 后端 API、数据库表、路由、文档保留，深链仍可访问（仅用于内部验证）；
- 不再对外承诺“到点自动开环境”：agent 目前没有订阅 `schedule.event` 下行，事件到点不会自动拉起 VM。

### 未来价值

可以根据课表**提前**调度：

- 开课前预拉镜像、预创建 VM、预热桌面；
- 到点自动启动、课后自动关机/回滚；
- 与房间启动配置（startup profile）结合，把“当前配置”升级为“时间段配置”；
- 与工单/审计/告警联动。

### 真实场景的例外（必须设计）

真实教室一定存在意外，排课调度不能是简单的定时器：

- 临时调课、补课、取消、延迟；
- 设备故障/离线、镜像拉取失败、磁盘满；
- 教师提前进入、拖堂、临时更换房间；
- 学生/考生误操作、断电、网络中断；
- 安全策略/考试模式临时变更。

因此未来排课调度至少需要：

1. **计划与实例分离**：周模板/课表生成实例，实例可单独覆盖；
2. **幂等执行**：同一时段重复触发不重复建 VM；
3. **人工接管**：教师/管理员可暂停、跳过、强制启动；
4. **失败回退**：预拉失败降级到现有镜像/已有 VM，不阻塞上课；
5. **宽限期与确认**：提前 N 分钟准备，到点确认，异常告警；
6. **全程审计**：谁在何时改变了哪个房间的期望状态。

## 3. 当前比赛范围（2026-11-14）

保留并演示：

- 身份链：房间/设备注册、在线/遥测、审计；
- 镜像：底包/ISO、镜像制作、发布/分配；
- 房间启动配置：自动拉镜像、自动创建/启动 VM、隔离网络；
- boot-display：启动步骤动画、VM 桌面（noVNC）、自动登录；
- 运维：WOL、优雅关机、最近电源事件、健康/工单；
- 多房间：1 区域 2 房间 2–3 设备。

隐藏、不现场演示：

- 课表、排课计划、触发事件；
- 联邦（代码已下线，仅保留未来规划）；
- 容器/GPU/P2P 等非核心能力。

## 5. 原则

> 先让一条真实教室链路稳定可演示，再谈跨房间/跨节点/排课自动化。
> 所有“未来能力”保留代码和数据模型，通过导航/配置收口，不做一次性删除。
